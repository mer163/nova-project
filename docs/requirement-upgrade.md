# 需求管理升级说明

参考六张飞书项目截图实现固定流程。字段目录中有大量系统信号、计算字段和业务专属指标，本期只纳入能够支撑创建、流转、人员协作与列表检索的字段；不引入通用工作流引擎。

## 字段与页面

创建页按基本信息、人员、文档与关联、版本与进度分组；详情页另有工作进展和操作记录；列表支持标题搜索、状态、需求负责人、优先级、模板筛选及创建时间/优先级排序，横向滚动显示测试、创建者、当前处理人、关联 Bug 数量等列。

| 类别 | 字段 | 约束 |
| --- | --- | --- |
| 基本 | 标题、描述、优先级 P0-P3、模板、产品方向、业务线、涉及端、风险、负责人 | 标题、优先级、至少一个涉及端、需求负责人必填；涉及端为固定枚举 |
| 人员 | PM、版本负责人、需求负责人、按端开发、UI/UX、测试、DA、技术评审负责人、关注人 | 协作角色只关联本需求，不改变全局 RBAC；每个协作角色当前可指定一人 |
| 文档与关联 | 需求文档、UI/UX 设计稿、技术文档、Test Case、关联 Bug | 文档只接受 HTTP/HTTPS 地址；Bug 必须存在 |
| 版本与进度 | 规划版本、实际上线版本、迭代、预计完成日期 | 迭代仍为文本，不创建迭代管理模块 |
| 系统 | 创建者、当前处理人、创建/更新时间、状态操作记录 | 由服务端生成；当前处理人按当前阶段的协作角色推断，未指定时回退到需求负责人 |

创建表单的“保存本机草稿”使用浏览器本地存储，仅保存在当前浏览器；正式创建会写入 MySQL。图片中的批量导入、文件上传、计算字段、业务指标和多人成员角色仍属于后续范围。

## 固定工作流

需求评审 → 技术评审 → 并行开发/用例设计 → Show Case → 第一轮测试 → 产品和设计走查 → 第二/三轮测试 → 功能服务上线 → Launch Review → 封版 → 集成测试 → 提审 → 已结束。

- 每次只前进或回退一个阶段。需求评审和技术评审可以拒绝；流程中的需求可以关闭。拒绝、关闭与已结束为终态。
- 开发阶段为所选涉及端创建并行任务，同时创建“用例设计与评审”。所有任务达到“已完成”或“跳过”后，才可进入 Show Case。各任务由对应开发或测试、需求负责人、产品经理及管理员更新；跳过仅产品经理或管理员可操作，须填写原因。跳过后可在开发阶段重新改为进行中。
- 首次进入开发阶段后，即使退回技术评审也不可更改涉及端，以免通过移除未完成任务绕过汇合条件。状态流转和并行任务变更均在数据库事务中加锁，服务端校验并记录操作人、时间、前后状态。
- 需求阶段由当前节点处理人流转，管理员可代操作。未设置节点角色时当前处理人回退到需求负责人。拒绝与关闭需要填写原因并记入操作记录；拒绝、关闭及已结束均为终态，本版本不提供恢复入口。协作角色、负责人、涉及端和计划/实际版本以及需求删除仅需求负责人或管理员可操作；普通编辑仅改动请求中实际提交的字段。这里的协作角色不授予全局 `items:update` 权限，调用接口仍需具备该权限。
- 节点处理人与跳过权限是本轮为防止越权而采用的保守默认规则。产品评审中关于终态恢复、按端跳过及测试/上线等节点的业务证据仍待负责人逐项确认；确认前不能将本规则视为已获产品验收。
- `GET /api/requirements/:id/history` 返回操作记录；`PUT /api/requirements/:id/tracks/:track` 更新并行任务，正文为 `{"status":"done"}` 等。需求列表另支持 `q`、`ownerId`、`currentOperatorId`、`template`、`sort`。

## 旧数据迁移与上线

Go 服务启动时先扩充表结构，再在一个数据库事务中把旧需求状态映射为：`pending` → `requirement_review`、`in_progress` → `development`、`done` → `finished`；`rejected` 与 `closed` 保留。旧需求缺失的模板、风险补默认值；已有负责人回填到需求负责人筛选列。原有需求和 Bug 记录不删除。旧需求的历史操作无法倒推，因此历史页显示为空。MySQL 的表结构变更不由这个数据事务覆盖，生产升级仍须先备份并演练恢复。

**生产升级前先备份 MySQL 并核对备份可恢复**，例如在原部署目录执行：

```bash
docker compose exec -T mysql sh -c 'exec mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" --single-transaction nova' > nova-before-requirement-upgrade.sql
test -s nova-before-requirement-upgrade.sql
```

备份文件包含用户和业务数据，应放在受控位置，不要提交到 Git。然后在测试库验证升级和流程，再滚动替换服务。回滚旧二进制前，应先恢复升级前的备份；旧代码不认识新状态。

本地验证：`cd frontend && npm run build`，`cd ../backend && go test ./...`。设置独立测试库的 `MYSQL_TEST_DSN` 可执行真实数据库的旧状态迁移、创建、并行汇合、操作记录、账号及权限集成测试。
