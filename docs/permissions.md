# 权限模型

Nova 的鉴权是两层的，两层都必须通过：

1. **全局角色**（用户级）：决定这个人在平台上能做什么，例如能否创建空间、能否管理成员、能否配置角色。
2. **空间成员角色**（空间级）：决定这个人在某个具体空间里能做什么，取值为负责人 `owner` / 可编辑 `editor` / 只读 `viewer`。

最终判定 = 全局能力 ∧（空间内是否具备该动作需要的成员角色）。

## 全局权限项

| 权限 | 说明 |
| --- | --- |
| `issue:read` | 查看工单 |
| `issue:create` | 创建工单 |
| `issue:update` | 编辑工单 |
| `issue:delete` | 删除工单、取消需求 |
| `issue:transition` | 推进状态 |
| `issue:comment` | 评论 |
| `issue:assign` | 指派负责人 |
| `space:read` | 查看空间 |
| `space:create` | 创建空间 |
| `space:manage` | 管理空间成员 |
| `member:manage` | 管理成员 |
| `role:manage` | 管理角色权限 |
| `workflow:manage` | 配置工作流 |
| `audit:read` | 查看审计日志 |

`*` 表示全部权限，仅内置超级管理员拥有。

## 空间成员角色

| 角色 | 读工单 | 写工单/评论/流转 | 管理成员 | 删除工单 |
| --- | --- | --- | --- | --- |
| `owner` 负责人 | ✓ | ✓ | ✓ | ✓（还需 `issue:delete`） |
| `editor` 可编辑 | ✓ | ✓ | ✗ | ✗ |
| `viewer` 只读 | ✓ | ✗ | ✗ | ✗ |

不在空间成员列表中的用户，即使管理员也无法从业务接口看到该空间的工单——列表接口会按成员关系过滤。管理员若需要处理某空间，需先把自己加入该空间。

## 流转权限

每条流转规则自带 `permission`，默认是 `issue:transition`。取消需求、不予修复这类终态操作要求 `issue:delete`，从而让「能不能废弃」和「能不能推进」分离。

## 服务端为准

前端会根据 `canEdit` 和角色隐藏入口，但所有写操作都重新在服务端校验：

- 未登录访问业务接口返回 `401`
- 无权限返回 `403`，错误信息明确指出缺哪个权限
- 非法状态流转返回 `409`，并附当前状态允许的下一步

## 审计

以下动作写入审计日志：登录、修改密码、创建/编辑/删除工单、状态流转、评论、成员增删改、角色增删改、工作流修改、空间创建与成员变更。日志记录操作人、动作、对象与摘要，可用于事后追溯。
